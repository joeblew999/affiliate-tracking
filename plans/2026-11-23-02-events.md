# 2026-11-23-02-events.md

The example host becomes what the real host is: people who already have an account buy a ticket to
an online event, and a partner earns commission on the tickets they bring. That replaces the Pro
subscription in the shop. The affiliate service changes very little, because a ticket is a one-off
Stripe payment, and the service already counts those.

## How a ticket is bought and credited

1. **A partner shares a link to an event.** This is a short link with the event's page as its
   destination, for example `/r/maya-launch` to `/events/<id>`. The service already has these
   (`db/schema/links.ts`, `destination`). Following it counts the click and sets the referral
   cookie, as now.
2. **The buyer is signed in on the shop.** Whoever brought them to the shop stays their partner
   for good, as now (`referrals`). If nobody did, the cookie from the event link counts.
3. **Buy ticket** on the event's page: one Stripe Checkout in `payment` mode, made by the shop's
   own page action. Better Auth's Stripe plugin only makes subscription checkouts, so the shop
   makes this one itself, with the official Stripe SDK. It carries what the service's `checkout()`
   call says to add: the partner's metadata, and their discount code if they have one, the same
   call the plugin made before.
4. **Stripe's `checkout.session.completed`** reaches the shop's Better Auth Stripe webhook, which
   passes it to the service, as now. The service records the sale.
5. **Commission:** the partner's percentage of the ticket, not counting tax. Or a fixed amount
   per ticket for one event, from a rule on that event's Stripe product. Both already exist
   (`commission_rules`: `percent`, `fixed`, `productId`).
6. **Hold, refund, payout:** unchanged. A sale waits `AFFILIATES_HOLD_DAYS`, then the daily job
   approves it. A refunded ticket, for example a cancelled event, comes off the sale, or is clawed
   back if it was already paid. A payout run pays partners by Stripe Connect transfer.

## Changes

### Shop (`apps/shop`)

- **Events:** each event is a Stripe product with a fixed id, so commission rules can name it.
  The demo has 3 events, in `apps/affiliates/demo.ts` with the rest of the demo, each with: a
  name, a simple description, a start and an end time, a location, and a ticket price. The
  shop creates the event's Stripe product the first time someone buys a ticket, if it isn't in
  Stripe yet.
- **Pages:**
  - the shop's page lists the events;
  - `pages/events/[id]` shows one event, with **Buy ticket**, or "You have a ticket" once
    Stripe has the paid checkout for this customer and event;
  - without a Stripe key, the page says the shop takes no payments.
- **Better Auth's Stripe plugin stays** for what it does: it makes the Stripe customer at sign-up,
  receives Stripe's webhook, and passes every event on. Its subscription part is removed, and so
  are the Pro plan, `STRIPE_PRO_PRICE_ID`, the Subscribe button and `listActiveSubscriptions`.

### Demo (`apps/affiliates/demo.ts`, both seeds)

- The Pro and Team products become 3 online events with prices. Every seeded sale is a ticket.
- **Seeded renewals and subscriptions go,** since the shop sells none. The service still handles
  renewals for hosts that sell subscriptions. Its dev test makes its own subscription sale first,
  instead of using a seeded one.

### Service (`apps/affiliates`)

- **Commission is on the price, not the tax** (`src/sales.ts`, `src/renewals.ts`). This is
  already done and tested, and waiting for the full run.
- **A partner's Stripe Connect account is made in the partner's own country:** they choose it
  before Stripe's onboarding. Today it's made without a country, so it lands in the platform's.

### Tests

- **Dev:** checkout events for tickets (`payment` mode, as most of them already are), with the
  amounts from the demo's events.
- **Stripe** (`e2e/stripe`):
  - a buyer signed up through Tom's link buys a ticket on Stripe's Checkout, and the sale is
    Tom's;
  - a payout of it is at the rate Stripe settled;
  - a buyer through Sam's link gets his discount;
  - a refunded ticket is refunded.
  The test-clock renewal goes, since there are no subscriptions. So do its helpers.

### README

- "How it works" and "Add it to your app" describe tickets: the host's own Checkout, the
  service's `checkout()` call, and the plugin's role. The webhook's events no longer need the
  plugin's subscription events.

## Stripe: two accounts (decided 2026-11-23)

Stripe handles all the tax. Partners are paid through Stripe Connect. Stripe won't allow both on
one account, so there are two, under one company (a US company through Stripe Atlas if needed):

- **The selling account** (the host's `STRIPE_SECRET_KEY`): Managed Payments, with Stripe as the
  seller, for the tickets (and any subscription). The shop's checkouts turn on
  `managed_payments`. They leave out what Managed Payments rejects: `automatic_tax`,
  `customer_update`, and Connect parameters. For Better Auth's subscription checkout,
  `getCheckoutSessionParams` overrides the plugin's default `customer_update`.
- **The payouts account** (the service's own key, `AFFILIATES_PAYOUTS_STRIPE_KEY`): a Connect
  platform. It holds no sales. Before each payout run, the service adds what's owed to its
  balance from the company's bank (Stripe top-ups, `topups.create`), then transfers to the
  partners as now.
- **The service reads sales from the selling account** (the exchange rate Stripe settled each
  sale at, a subscription's first payment) with a read-only key for it,
  `AFFILIATES_SALES_STRIPE_KEY`. It pays from the payouts account. The two keys are never
  confused, because each Stripe call names which account it's for.
- **Promotion codes** live in the selling account, so the partner's discount is made with the
  selling key.
- **Tests:** the Stripe suite needs two test-mode accounts and keys,
  `STRIPE_TEST_SECRET_KEY` (selling) and `STRIPE_TEST_PAYOUTS_KEY` (payouts). Top-ups in test
  mode come from Stripe's test bank account.

## Still open

- **Stripe's yes on three things**, asked by Gerard (checked against Stripe's docs 2026-11-23):
  - that live online events qualify for Managed Payments (it covers digital products, but not
    services with human involvement such as live 1-1 coaching:
    docs.stripe.com/payments/managed-payments/eligibility);
  - top-ups for the payouts account (generally available in the US, UK and Japan, a private
    preview in Australia: docs.stripe.com/connect/top-ups);
  - paying partners outside the US, UK, EEA, Canada and Switzerland (not self-serve from any
    platform: docs.stripe.com/connect/cross-border-payouts-to-recipients).
- **The hold period:** it's counted from the purchase, not the event's date. A ticket for an event
  more than `AFFILIATES_HOLD_DAYS` away is approved before the event happens. If events are often
  further away than that, the hold should end after the event.
