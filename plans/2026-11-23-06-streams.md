# plans/2026-11-23-06-streams.md

The control plane and the tests, rebuilt on the Durable Streams protocol where it fits Void and
React. Follows `plans/2026-11-23-05-activity.md`, which says what the control plane is and what was
built first.

## Where things are (2026-11-23)

- The shop runs their Cloudflare server inside itself (`@durable-streams/server-cloudflare` 0.1.1):
  `apps/shop/durable-objects/streams.ts`, `src/streams.ts`, `routes/streams/[...path].ts`.
- The Activity pane reads its viewer's stream with their client (`@durable-streams/client` 0.2.7).
- Both apps are deployed with it. The dev suite passes: 29 tests, about 10 minutes.

## What the protocol gives, and what their Cloudflare server has

Read from `PROTOCOL.md` in `durable-streams/durable-streams` (checked 2026-11-23).

| Part of the protocol                              | In their Cloudflare server | Use here                         |
| ------------------------------------------------- | -------------------------- | -------------------------------- |
| A stream is a URL: create, append, read, delete   | yes                        | yes, already                     |
| Read from an offset, then live (SSE or long-poll) | yes                        | yes, already                     |
| Closing a stream: a real end, readers see it      | yes                        | step 3 below                     |
| Expiry (unused for a time, or at a date)          | yes                        | yes, already (30 days unused)    |
| Idempotent producers (the same write sent twice)  | yes                        | not needed: events are keyed     |
| Forks (a copy from a point, nothing copied)       | yes                        | not while the data is in D1      |
| Subscriptions (wake a worker, a saved offset)     | **no** (answers 404)       | with Void, when needed: see last |

Their state format (`@durable-streams/state`): events that insert, update or delete a thing by
its type and key, and a reducer that keeps the latest of each. Its TanStack DB layer is not used:
it would be a second way to hold a page's data beside Void's loaders.

## What gets built, in this order

Speed first, because the tests are what hurt now.

### 1. Tests: the apps started once, not once per file

Done (2026-11-23). The dev suite: 29 tests, 619 seconds before, 227 now.

- One pair of apps for the whole run (`e2e/apps.ts`).
- Between files the demo is put back by the apps themselves: an admin's "Reset demo", an action
  in the control plane like any other (`apps/affiliates/src/demo-reset.ts`).
- The test helpers no longer open the admin page again every time they look at it. The pane says
  when the page has reloaded its data after an action (`data-page`), and the helpers wait on that.
  That alone took a payout test from 15 seconds to 2. It also showed a wait that had been missing:
  the daily job's helper never waited for the job, and the reload had been hiding it.

Still one file at a time, and staying so. The program is one program: a payout run or the daily
job touches every partner, so two files on one database would act on each other's people. Side
by side would need the program split by a key, each test with a program of its own. Decided
against (2026-11-23): a deployment is one program, so that key would exist for the tests alone.

### 2. A page arrives already caught up

Done (2026-11-23).

- A page comes with its viewer's latest activity (Void's shared data, set in each app's
  middleware for a page itself; the service asks the shop). The pane starts with it, says
  "connected" from the first paint, and reads on from the offset it came with.
- "Latest" is the last 30 actions, not the whole stream: the shop notes where each action starts
  in a viewer's stream (`apps/shop/durable-objects/recent-actions.ts`) and a page reads from the
  oldest of those. So a stream growing doesn't slow every page, which with one pair of apps for
  the whole test run it otherwise would. An action still running from more than 30 actions ago
  isn't shown.
- Every test helper that opened the admin page again to watch or to look now uses the page
  that's open.

Found on the way, not explained: with the admin's page in a background tab (a second tab opened
in the same browser), its reload of data after an action didn't finish, and the page stayed
busy. One test did that; it now reads from the admin's own tab. To look into: whether a real
user's background tab does the same and recovers when looked at.

### 3. Their state format, and closing

- Events become their kind: insert or update of an `action` or a `step`, by key. The reducer is
  theirs (`MaterializedState`), the same in the loader and the browser. `apply()` goes; what's
  left of ours is working out an action's state from its steps.
- An action's own stream, closed when it finishes, is the protocol's way to say "this is done"
  as a fact. To decide before building: the pane would then hold one live connection per running
  action, and a browser allows about six to one site over the dev server's kind of connection.
  If that can't be made safe, a viewer keeps one stream as now, split by day so it can't grow
  without end, and nothing is closed.

### Later: workers reacting to each other's events

Their Cloudflare server has no subscriptions. Their Node server does
(`packages/server/src/subscription-*.ts`), and the protocol says exactly how they behave
(sections 6 and 7: a wake, an offset saved per subscriber, a lease). When a worker here needs to
react to events, that is ported, following the protocol, with Void's pieces:

- the wake is a call over a service binding to the worker's route, which only queues it;
- the worker's queue consumer reads the stream from its saved offset and saves the new one in the
  same D1 batch as its work;
- the daily job does the same read, in case a wake was lost.

Nothing subscribes to anything today, so none of it is built yet.

What reading their code showed (2026-11-23, `durable-streams/durable-streams` at `461b402`):

- Their Cloudflare server has never had subscriptions: it arrived in one pull request (#392), and
  there is no pull request or issue for them.
- Their Node server's version (`subscription-manager.ts`, `subscription-routes.ts`,
  `subscription-types.ts`, added in #361) keeps everything in memory, with timers. It shows the
  behaviour, not how to make it last. So this is a design job, not a line-by-line port.
- What is different on Cloudflare:
  - No one place sees every append: each stream is its own Durable Object. A stream has to keep
    the list of subscriptions linked to it and tell each one when it's appended to.
  - A pattern such as `events/*` needs to know of new streams. There is no list of streams. A
    small directory of patterns, asked once when a stream is made, not on every append.
  - One Durable Object per subscription, as the protocol's own wording has it, holding the saved
    offsets, the lease and the wake counter in SQLite. Leases and retries are alarms.
- Delivery is a signed HTTP POST to a URL (Ed25519, keys published at `__ds/jwks.json`), `https`
  only, except localhost. A service binding is not a URL. Either workers are called at their
  public address, or the library takes the function that delivers, and the app passes its binding.
- The other kind, pull-wake, needs a worker that stays connected to a wake stream. That doesn't
  suit a Worker; webhook is the kind to use.
- Their conformance tests have subscription tests, off by default. Turned on, they say whether a
  Cloudflare version behaves as the protocol says.
- Done properly it is built in a fork of their repo, inside `packages/server-cloudflare`, passing
  their tests, and offered back to them.

Read since (same day): their subscription tests, and Void's durable state.

- The tests are six, about 375 lines (`packages/server-conformance-tests/src/index.ts`, from line
  11354, run only with `subscriptions: true`): create and re-confirm; refuse an unsafe webhook
  address; a webhook answering `done` acknowledges the wake; a callback acknowledges and a
  repeat of it is refused as stale; adding and removing a stream by name; and pull-wake's claim,
  acknowledge and release. They write to streams over plain HTTP at `/v1/stream/<path>` and use
  the pattern `events/*`, so a new stream matching a pattern must wake its subscriber. They don't
  test surviving a restart, retries, or a lease running out.
- Void can carry most of it, without changing their server:
  - **The subscription's state** in Void's `defineDurableState`: a typed, saved value with
    methods the app's server code calls directly, and an `alarm` (for a lease running out, and
    for trying a delivery again).
  - **Seeing appends**: a wrapper round their handler. After a write they answer as accepted, it
    tells the subscriptions linked to that stream. Every write goes through the handler, the
    shop's own included, so nothing inside their Durable Object has to change.
  - **Patterns**: a small directory of subscriptions and their patterns, also durable state, read
    by the wrapper.
  - **Delivery**: over a service binding to the subscriber's route, which queues it (Void's
    queues); the consumer reads the stream from the acknowledged offset, saves its work, and
    calls back to acknowledge.
- What that leaves weaker than doing it inside their Durable Object: the write and the telling
  are two steps. If the worker dies between them, that wake is lost until the stream's next
  write, or until a daily check that compares each stream's end with what's acknowledged.
- Built and proved the same day: `packages/streams`. Their whole conformance suite passes against
  it in a Void app under `vp dev` (338 tests, the six subscription ones among them), and so do
  six tests of this repo's for what theirs leave out: a lease running out, a failed delivery
  tried again, following a stream from where it ends, a pattern that could cover any stream, a
  subscription deleted mid-wake, and a wake still to send being sent after the app stops and
  starts again (`vp run test:streams`).
- In the apps since (same day): the shop mounts it at `/streams`, its route deciding who may call
  what; a new user is published to `events/signups` and the service follows it (a wake over its
  binding, checked by its signature, queued, read on, acknowledged); a daily check in the shop;
  and in the Activity pane the subscriber's part is a step of the sign-up's own action. The old
  path (the shop's `affiliate-signups` queue, the service's `/api/host/signup`) is gone.
- Deployed and checked on the live site the same day: a new account made on the live shop, and
  in the admins' stream its "Sign up" action went shop done, publish done, the service's part
  waiting, then "Sign-up recorded" done by the service. So the alarm, the wake over the
  binding, its signature, the queue, the read and the acknowledgement all work on Cloudflare.
- Still open:
  - the live service isn't marked as a demo site (`AFFILIATES_DEMO`), so it has no "Reset demo"
    button: that button deletes everything in the live database, and turning it on is the
    owner's to say;
  - a subscription whose settings change (the service's address, say) is refused as different,
    loudly. Moving one on while keeping how far it had got isn't built;
  - a viewer's stream is written straight to its object, not through the subscriptions, so
    nothing can subscribe to the Activity pane's streams;
  - a pattern whose first part is a wildcard is told of new streams, but isn't given the
    streams already there when it's made (there's no one list of them all).
