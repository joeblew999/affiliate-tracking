# plans/2026-11-24-02-hub.md

The streams become a worker of their own, the hub, which every other worker uses the same way.
Then results go on the streams, and tests go over them. Replaces
`plans/2026-11-24-01-tests-without-a-browser.md` (its measurements are kept below) and takes
over what `plans/2026-11-23-06-streams.md` left open.

## What was wrong (2026-11-24)

- **The streams lived inside the shop** (`apps/shop/durable-objects/`, `src/streams.ts`,
  `routes/streams/`), because the shop holds the sign-in. So every worker reached the bus through
  the shop. Wrong for two workers, unworkable for twenty.
- **Unfinished:** only the sign-up went over it; it carried "started, done, failed" but no
  results; a live sign-up took 5 to 15 seconds to reach the service.
- **The tests were modelled on how Void tests Void** (copy an app, start a dev server, drive a
  browser, allow two minutes), and used that for everything, sums included.
- **Every queue waited up to 5 seconds** before handing a message over: none of the six set
  `maxBatchTimeout`, and Void's default is 5 (its `guide/queues.md`).

## 1. The hub: `apps/hub`

A Void app with nothing in it but the streams. It knows no users, no shop and no stream names.

- **What it holds:** their stream server (`@durable-streams/server-cloudflare`), and the
  subscriptions, directory and signing key from `packages/streams`: `durable-objects/`.
- **Who may call it:** workers, over a service binding, with `HUB_TOKEN`. It has no public
  address. A subscriber answering a wake is let in by the wake's own token, as the protocol says.
- **Browsers** read at their own app's `/streams/<viewer>`. That app knows who is signed in,
  decides, and passes the read on to the hub. So the hub needs no sign-in.
- **A worker that follows a stream says so itself** (a subscription, made once in each run of
  the worker), giving its own address. The hub sends the wake there, signed, as the protocol's
  webhooks work; the worker checks the signature against the hub's key. The hub has no bindings
  and no list of anyone: adding a worker to the bus changes nothing in the hub.
- **Its client**, `apps/hub/client.ts`, is what the other workers call it with; each call is
  defined once, in `apps/hub/src/contract.ts`.
- **Beyond the protocol**, three routes of the hub's own: `/api/append` (one event to several
  streams, without looking for subscribers), `/api/recent` (a stream from its last 30 marked
  places; the protocol has no "read the latest") and `/api/publish` (a write that answers with
  the subscriptions told). To look at again: which can be plain protocol requests.
- **The daily check** (a subscriber woken if a stream has gone past what it acknowledged) moves
  to the hub, for every subscription there is.
- **Out of the shop:** its five durable objects, `src/streams.ts`, `crons/daily.ts`, and the two
  routes the service used to reach the streams through it
  (`routes/api/affiliates/activity.ts`, `recent.ts`).

**Not deployed yet, and local `vp run dev` of the shop needs the deploy.** The shop's
`void.lock.json` still records the five durable objects that left it, and with them recorded and
not defined the shop's dev server doesn't start (`void info` lists them). Void's guide
(`guide/durable-state.md`) says a deployed durable object is removed by a deploy
(`void deploy --platform cloudflare --atomic`), which writes the removal to the lock; the lock
isn't edited by hand. So the order is: deploy the hub, then the shop (with `--atomic`), then the
service, with `HUB_TOKEN` in all three and the service's `AFFILIATES_SITE_URL`. The tests'
copy leaves the lock out (`e2e/apps.ts`), so they run before that.

## 2. The delay

Each queue hands a message over at once (`maxBatchTimeout = 0` in all six). The sign-up crossed
two of them (the shop's `published`, the service's `wakes`): up to 10 seconds of waiting for
nothing. To be checked live at the next deploy.

## 3. Results on the streams

Durable State (`@durable-streams/state` 0.3.2, released 2026-09-10): typed changes of a thing,
by type and key. The code that saves something writes it as it now stands (an upsert), as part of
its step, to a state stream of each viewer the action concerns (`state/<viewer>`, beside their
stream of the actions). Not a second copy of the database kept in step by something else: only
the outcome of each action, from the action.

- `packages/activity`: `outcome()` (`src/server.ts`), `stateStreamOf()` (`src/model.ts`).
- `apps/affiliates/src/outcomes.ts`: the schema (sales, payouts, partners, links, referrals and
  events, each from its table) and the functions that write them.
- Written where each is saved: a checkout's sales and a renewal, refunds and clawbacks (every
  sale of the payment), the hold, an admin's decision and bonus, a payout (it and its sales),
  booking an event and putting it on sale, applying, an admin's change to a partner, a new
  organiser or venue contact, a link made or archived, a referral recorded or settled.
- **Not written:** a partner's Stripe account being connected (`pages/index.server.ts`), a
  promotion code made outside an admin's change (`src/approval.ts`), a venue (`src/payees.ts`),
  a payout's later changes by the payouts webhook, and clicks (a click isn't part of any action).
- The control plane's own events (started, step) are still their own shape, not Durable State.
- Several changes go to the hub in one request (`/api/append` takes a list).

## 4. Tests over the bus

A test sends the event or makes the call, waits on the stream for the action to finish, and reads
the result from the state stream. No browser: `e2e/dev/bus.ts`. A seeded row nothing wrote is as
the fixtures have it. The demo is put back between files the same way.

- **Over the streams:** `money`, `flows`, `events`, `hold`, `payouts`, `refunds`.
- **In a browser, being about what a page shows:** `pages` (with a partner's click count, the
  admin Events tab's money and an organiser's page, moved there), `activity`, `streams`, `demo`.

## Open, carried over

- A subscriber whose address changes: the hub answers its subscription with 409 (the protocol:
  a subscription that exists with other settings), and goes on waking the old address. The
  tests met this (new ports each run) and now start the hub empty each run. For a live worker
  that moves, there's no way yet to move its subscription and keep its place.

- A page left in a background tab stays "reloading" (seen 2026-11-23, cause unknown).
- A stream only grows; a page reads its last 30 actions, but the stream itself is never trimmed.
- The Stripe suite hasn't been run since the control plane was built.
- CI runs the protocol's 338 conformance tests on every push; to be cut to our own subscription

- `AFFILIATES_DEMO` on the live demo: only on the owner's say.
