# 2026-11-23-05-activity.md

What the system does shows itself as it happens, on every page: for the people using it, and for
the tests, which use the system the way people do. This replaces `2026-11-23-04-live-events.md`
(hand-written announcements and `watch()` in the tests).

## The idea

The system's own running is a stream of events: this request ran, that queue step finished, this
email went out, that step failed. Three things use it:

1. **The events are part of the system, not added by hand.** They come from the primitives work
   runs on, so no app code announces anything.
2. **The Activity pane is on every page of both apps.** It shows the viewer's actions and what
   each one caused, live, with each action marked done or failed.
3. **The pages keep themselves current from the same stream.** When work the viewer can see
   finishes, the page reloads its data (Void's `router.refresh()`), at most once at a time.

It's event streaming with tracing. It isn't event sourcing or CQRS: the database stays the
truth, and the events are notices that something happened. Nothing is rebuilt from them, and
losing one loses no data.

## 1. The events

Each app has one module that wraps the five ways work happens. The app uses these and not
Void's own, and a lint rule (`no-restricted-imports`) keeps it that way.

| Work            | Events                                                                                                                       |
| --------------- | ---------------------------------------------------------------------------------------------------------------------------- |
| A request       | One middleware: every non-GET request (page actions, routes, Stripe's webhook), with its status, and the reason when refused |
| A queue         | `queued` when sent; `running`, then `done` or `failed` with the error, from the wrapped `defineQueue`                        |
| A scheduled job | `running`, then `done` or `failed`, from the wrapped `defineScheduled`                                                       |
| An email        | `sent` or `refused` for each one, from the wrapped `sendEmail`                                                               |
| The other app   | Calls over the binding carry the work's identity, so its events join the same action                                         |

**Every event carries the action that started it.** A request that isn't part of earlier work
starts an action and gets its id. Every message it queues carries that id, and so does each
message those queue, and each call to the other app. One press of **Book event** gives one
group: the venue's payout, on sale, the shop told, the email batches.

**Done is counted, not announced.** Per action, each `queued` adds one pending step and each
`done` takes one away. At zero pending, the action is done. If any step failed, it's failed.

**The lines are about the work:** the step, its outcome, and the error. They carry no business
details (no commissions, no emails), so whoever sees an action sees nothing of anyone else's.

## 2. Who sees what

Void's live streams (`void/live`): a topic for each person (`user:<id>`), and `admins`.

- An action goes to the person who started it, and to admins.
- Work nobody signed in started (Stripe's webhook, the daily job) goes to admins.
- The rule is in `onSubscribe`: a connection may subscribe to its own `user:` topic, and an
  admin also to `admins`. Not signed in, nothing.
- One stream, the service's. The shop's `/live` passes the connection through to the service
  over the binding, so every page connects to its own address and its sign-in cookie just
  works. The shop's events reach the service the same way.

Void allows 256 watchers per topic. Per-person topics have one or two, and `admins` a few.

## 3. The pane

- **On every page, in both apps' layouts:** the viewer's actions, newest first, each with its
  steps, and done, pending or failed (in red, with the step and its error).
- **Live only.** It shows what happens while the page is open. The lasting record is what the
  pages already show: sales, payouts, events.
- **The connected mark:** `data-live="connected"` once the page's subscriptions are registered,
  shown as a "Live" dot, and `reconnecting` while the connection is down.
- **Structured marks for the tests,** as attributes on each action: its id, what started it, and
  its state. People read the words, the tests read the marks.

## 4. The tests

All through Playwright, on the real pages, as people use them:

1. Open the page of each person the step concerns, and wait for each pane's connected mark.
2. Act: press the button, wherever it is.
3. Wait for that action in the pane to read done or failed. Failed fails the test at once, with
   the step and its error.
4. Check the result on the page, which has already reloaded its data.

A test doesn't need to know which queues an action uses or how many steps it has. Playwright's
own timeout is left only as the backstop for "the app never answered". Each time it fires, that's
a bug in this system.

Node is left running the apps and being the clock (Void's trigger for the daily job). Stripe's
part moves to Stripe's test mode, driven from the pages: a separate plan.

## Built so far, and how (Void's own pieces)

- `packages/activity`: the model (`model.ts`), the wrappers (`server.ts`), which action work belongs
  to (`trace.ts`), and the pane (`pane.tsx`). Nothing in it knows the apps.
- The control plane is a Void WebSocket room in the shop (`routes/activity/[viewer].ws.ts`): one per
  viewer, Void auth's `ctx.user` deciding who may watch, its storage holding the viewer's actions.
  The service's pages connect to it as a trusted origin; the service's work records into it over
  the binding (`/api/affiliates/activity`).
- `AsyncLocalStorage` carries the current action within a request or a queue message: Void turns
  on the `nodejs_als` flag for every app (it uses it for `getUser()`).
- A request's own step is recorded done after its response has gone (`waitUntil`), so "done" can't
  reach a page before the answer it's about.
- The pane reloads the page's data only when the page is idle (`useNavigation()`), from the message
  handler, never during a state update.

## Learned, and still to do

- **The browser is part of the system.** The control plane said "done" while the person's request
  had been aborted. Each page reports its own side too (each form's result, from `useForm`, and
  script errors), as steps of the same action, so done means the person has their answer.
- **The wrappers stand in for hooks Void doesn't have.** Ask VoidZero for one place to observe every
  request, page action, queue message, scheduled run and email with its outcome; until then the
  wrappers stay thin, in one package.
- **The test harness copies the repo's own packages** into each run, so edits can't reach a running
  test; stops its apps however a run ends; and shows the apps' output with a failed test.

## Still to check in Void, before building

- that a middleware sees page actions with their final status, and the reason when refused;
- that the action's id can ride on queue messages and binding calls without app code touching
  it;
- that Cloudflare's own Worker tracing can't feed a live pane in the app. If it can, it's the
  source instead of the wrappers;
- that counting pending steps holds up when Void's live delivery (at most once) drops an event.
  An action that never completes is shown as such, never hidden.

## Known limits

- Live only: a person who wasn't looking doesn't see a failure in the pane. So every failure
  also stays on the thing that failed (a payout's status, an email batch, a Stripe event).
- Each signed-in tab holds a live connection to a Durable Object. For customers, the pane
  connects only on pages where something of theirs can happen.
- The shop's activity runs through the service. With the service down, the shop's pane is too.

## Replaces

- the hand-written `announce()` calls and each app's `src/live.ts` topics;
- the tests' `watch()` and the `eventsource` package;
- reading the apps' logs for "failed" lines in `e2e/apps.ts`.

## Many workers: the hub as an event bus

The pattern is event-driven architecture: independent workers around one shared event bus, each
publishing what it did and reacting to what it cares about. Nobody defines the overall flow; it
emerges. Every event carries the id of the action that started it.

- **The hub is its own worker** (`apps/activity`): the event bus, and the Activity pane's source.
  The rooms move out of the shop. It asks the shop's Better Auth who is signed in.
- **Workers publish and subscribe through the hub** for things that happened (a sign-up, a Stripe
  event, an event going on sale), in place of calling each other. The hub delivers each event to
  each subscriber's queue, so it survives a crash and is retried.
- **Questions that need an answer stay direct calls** ("who is signed in", "what goes on this
  checkout").
- **Each worker's event names and shapes are its contract,** checked by the hub.
- Not CQRS: each worker's own database stays the truth.

## Testing, as two separate things

1. **Each repo's own Playwright tests** (settled): ordinary tests of that worker with the hub,
   run in that repo, start to finish. They press things on the worker's pages and watch the pane.
   Open: where an event comes from that another worker would send, when the worker is tested
   alone. Proposed: a page on the hub where an admin publishes an event by hand (also how a
   person re-sends one after a fix). Not yet agreed.
2. **The whole system, all workers together** (open): something has to play each worker's users.
   A repo's test suites can't simply all run at once: each test is self-contained, starts its own
   copy of the apps, and isn't built to wait on another repo. One answer is robot users: a
   long-running Playwright script per role, in the repo that owns those pages, acting when it
   sees its cue in the pane, with the run failed by any failed or stuck event anywhere. Not yet
   agreed.

## To fix on the way, or the pane misleads

- an action shows to the people it concerns, not only whoever started it;
- a step stuck queued or running (a send that failed, retries used up) is shown as stuck;
- the browser's side of each action;
- one admins' room takes every event in the system: split it before real volume.
